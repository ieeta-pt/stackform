description: "What each v0.1 key does: collections, fields, payload validation, authentication, roles, access rules, soft delete, pagination, security and build errors."
---

A v0.1 spec declares MongoDB collections and gets a CRUD API for each of them.
`stackform run spec.yaml` serves the spec with the development server, and
`stackform build spec.yaml -t fastapi|drf|raw` generates a FastAPI, Django REST
Framework or raw-ASGI backend with the same behaviour. The
[grammar reference](./grammar-reference.md) lists every accepted key.

## 1. Top-Level Sections

| Section | Required | Purpose |
|---|---:|---|
| `version` | yes | Always `"0.1"`. |
| `api` | no | Route prefix, pagination and the operations every collection serves. |
| `mongo` | no | The MongoDB connection. |
| `security` | no | CORS and standard security headers. |
| `providers` | no | Named OIDC or SAML providers that `auth.via` may list. |
| `collections` | yes | The data model: one entry per MongoDB collection. |
| `ui` | no | A generated frontend; see the [UI reference](../v0.2/Reference/ui/overview.md). |

Every object in the spec is closed. A misspelled or unknown key fails the build
with `SCHEMA_VALIDATION_ERROR`, naming the key and its path.

## 2. Interpolation

Any string value may read the environment when the spec is loaded:

- `${VAR}` takes the value of `VAR`; the build fails with
  `INTERPOLATION_MISSING_VAR` when it is unset.
- `${VAR:-default}` takes `default` when `VAR` is unset.

Inside a YAML flow mapping (`{ ... }`), quote the value: `database: "${MONGO_DB}"`.
See [environment variables and interpolation](../v0.2/Reference/configuration/environment-variables.md).

## 3. Collections

`collections` maps each collection name to its configuration. The name is the
MongoDB collection and the route segment.

| Key | Default | Meaning |
|---|---|---|
| `type` | `base` | `auth` makes the collection an identity collection (section 6). |
| `fields` | required | The record fields (section 4). |
| `auth` | - | Required when `type: auth`. |
| `roles` | - | Roles of an auth collection (section 7). |
| `operations` | `api.operations.defaults` | Which CRUD operations the collection serves (section 8). |
| `access` | public | Who may call each operation (section 9). |
| `softDelete` | `false` | Delete stamps `deletedAt` instead of erasing (section 10). |

Each collection declares exactly one field of `type: id` (`ID_FIELD_MISSING`,
`ID_FIELD_MULTIPLE`). The server generates its value on create (UUIDv7, or UUIDv4
with `format: uuidv4`); a request body that sends it is rejected with 422.

## 4. Fields and Payload Validation

Every field accepts `type`, `required` and `default`; top-level fields also
accept `unique`. The other keys depend on the type:

| Type | Extra keys | Accepted JSON value |
|---|---|---|
| `string` | `minLength`, `maxLength`, `format` (`email`, `e164`, `uri`, `uuidv7`, `uuidv4`) | a string |
| `number` | `min`, `max` | a number; a numeric string is rejected |
| `boolean` | - | `true` or `false` |
| `datetime` | - | an ISO 8601 date or date-time string |
| `enum` | `values` (required) | one of `values` |
| `array` | `items` (required): a nested field | a list whose items satisfy `items` |
| `object` | `properties`, `additionalProperties` | an object |
| `ref` | `ref` (required): a collection name | the id of a record in that collection |
| `id` | `format` (`uuidv7`, `uuidv4`) | generated by the server |

A key that does not belong to the field's type fails the build with
`SCHEMA_VALIDATION_ERROR`. The build also checks that:

- `min` is not greater than `max`, and `minLength` not greater than `maxLength`
  (`FIELD_CONSTRAINT_INVALID`);
- a `default` satisfies the field's own keys, nested properties and items
  included (`FIELD_CONSTRAINT_INVALID`);
- `ref` names a declared collection (`REF_TARGET_NOT_FOUND`);
- collection and field names are identifiers: a letter followed by letters,
  digits or underscores, neither a Python keyword nor a name the generated
  models reserve (`INVALID_NAME`, `INVALID_FIELD_NAME`).

Request bodies are validated alike by the development server and every
generated backend, and an invalid body answers 422:

- A field the collection does not declare is rejected (`Unknown fields: <name>`).
- `required` fields must be present on create and replace; update (`PATCH`)
  accepts any subset of fields, the empty body included.
- A field left out of a create keeps its `default` when it declares one and is
  otherwise absent from the stored record.
- An `object` field with `properties` is closed: a key it does not list is
  rejected unless `additionalProperties: true`. An `object` field without
  `properties` accepts any keys.
- `datetime` values are stored and returned as UTC timestamps: `"2024-01-01"`
  becomes `"2024-01-01T00:00:00+00:00"`.
- `unique: true` creates a unique index; a create or update that repeats a
  stored value answers 409.

## 5. API Section

| Key | Default | Meaning |
|---|---|---|
| `api.basePath` | `/api` | Prefix of every route. |
| `api.version` | none | Second prefix segment: `/api/v1/...` with `version: v1`. |
| `api.pagination` | see section 11 | List page sizes. |
| `api.operations.defaults` | every operation on | Operations every collection serves unless it overrides them. |

## 6. Auth Collections

A collection with `type: auth` holds identities that callers authenticate as.

```yaml
collections:
  users:
    type: auth
    auth:
      identifier: email
      via: [password, apiKey]
    fields:
      id: { type: id }
      email: { type: string, required: true, unique: true }
      apiKey: { type: string, required: true }
```

`auth.identifier` names the field that identifies the caller
(`AUTH_IDENTIFIER_FIELD_NOT_FOUND` when the collection does not declare it); mark
it `unique: true`. `auth.via` lists how callers authenticate: `password`,
`apiKey`, or the name of an entry under `providers`
(`AUTH_VIA_UNKNOWN_PROVIDER` otherwise).

### Password

- The create body carries a `password` field the spec does not declare; it is
  required (422 without it). Declaring `password` or `passwordHash` in `fields`
  fails the build (`AUTH_PASSWORD_FIELD_FORBIDDEN`,
  `AUTH_PASSWORD_HASH_FIELD_FORBIDDEN`).
- `POST {prefix}/{collection}/login` with the identifier and `password`, for
  example `{"email": "ann@example.com", "password": "..."}`, returns
  `{"token": "<JWT>", "user": {...}}`. Wrong credentials answer 401
  `{"detail": "Invalid credentials"}`.
- Requests authenticate with `Authorization: Bearer <token>` or with HTTP Basic
  credentials (identifier and password).

### API key

- The collection declares an `apiKey` field (`AUTH_API_KEY_FIELD_MISSING`
  otherwise). The key sent on create is stored hashed.
- Requests authenticate with the `X-API-Key` header or `Authorization: Bearer <key>`.

Passwords, password hashes and API keys are never returned by any route.

### Providers

`providers.<name>` declares an OIDC provider (`client_id`, `client_secret`) or a
SAML provider (`idp_metadata_url`, `sp_entity_id`); `auth.via` may list its name
next to `password` and `apiKey`. Each provider type accepts only its own keys.

```yaml
providers:
  corporate:
    type: saml
    idp_metadata_url: ${SAML_IDP_METADATA_URL}
    sp_entity_id: https://sp.example.com/metadata
collections:
  users:
    type: auth
    auth: { identifier: email, via: [password, corporate] }
```

A SAML provider listed in `via` signs users in through the
[SAML routes](../v0.2/Reference/providers/saml.md#generated-routes) under the
collection path (`/api/users/auth/corporate`, its `/callback`, `/metadata` and
`/logout`). The assertion's NameID fills the collection's `identifier`, and a
user signing in for the first time gets a new record. The login code the callback returns is redeemed at `POST /api/auth/exchange`
for the app token, and the generated UI offers sign-in through the provider.
`stackform run` and the `fastapi` target serve these routes; the `drf` and `raw`
targets and `stackform run --raw` reject the provider with
`BACKEND_FEATURE_UNSUPPORTED`.

## 7. Roles

An auth collection may declare roles:

```yaml
    roles:
      values: [reader, editor, admin]
      default: reader
      hierarchy:
        admin: [editor]
        editor: [reader]
```

- Every new identity receives the `default` role. A request body cannot set
  roles; they are stored with the identity's credentials, under `_auth.roles`
  in its MongoDB document.
- `hierarchy` maps a role to the roles it includes, transitively: with the
  hierarchy above an `admin` passes an `editor` or `reader` rule.
- `default` and every role named in `hierarchy` must be one of `values`
  (`ROLES_DEFAULT_UNKNOWN_ROLE`, `ROLES_HIERARCHY_UNKNOWN_ROLE`), and the
  hierarchy cannot be circular (`ROLES_HIERARCHY_CYCLE`).
- `roles` is accepted only on a `type: auth` collection.

## 8. Operations and Routes

Each enabled operation serves one route under `{basePath}[/{version}]`:

| Operation | Route | Success |
|---|---|---|
| `list` | `GET /{collection}` | 200, a JSON array |
| `get` | `GET /{collection}/{id}` | 200 |
| `create` | `POST /{collection}` | 200, the stored record |
| `update` | `PATCH /{collection}/{id}` | 200, the updated record |
| `replace` | `PUT /{collection}/{id}` | 200, the replaced record |
| `delete` | `DELETE /{collection}/{id}` | 200 |

An auth collection whose `via` includes `password` also serves
`POST /{collection}/login`.

Every operation is on unless `api.operations.defaults` turns it off;
`collections.<name>.operations` overrides the defaults for one collection. A
disabled operation has no route.

## 9. Access Rules

`collections.<name>.access.<operation>` decides who may call the operation. An
operation without an access entry is public. `replace` without an entry of its
own uses the `update` entry.

An entry is a principal or a list of rules:

| Principal | Who passes |
|---|---|
| `public` | Anyone, authenticated or not. |
| `"*"` | Any authenticated caller. Quote it: a bare `*` is a YAML alias. |
| `<authCollection>:*` | Any identity of that auth collection. |
| `<authCollection>:<role>` | An identity of that collection holding the role. |
| `<role>` | The role on the only auth collection (`ACCESS_AMBIGUOUS_ROLE` with several). |

A principal naming an undeclared auth collection fails with
`ACCESS_UNKNOWN_ENTITY`; a bare role in a spec without auth collections fails
with `ACCESS_NO_AUTH_ENTITY`.

A rule adds a condition and a refusal message:

```yaml
    access:
      get:
        - principal: "users:*"
          when: principal.sub equals document.ownerId
          reason: Only the owner can read this post.
```

- `when` is a [when expression](../v0.2/Reference/when-expressions/overview.md)
  over `principal` (`principal.sub`, `principal.roles`, `principal.record.<field>`)
  and `document`, the record the route addresses. A `create` rule has no record,
  so naming `document` there fails with `ACCESS_RULE_INVALID`; a malformed
  expression fails with `WHEN_EXPR_INVALID`.
- Rules are tried in order and the first that admits the caller decides. A
  `public` rule makes the operation public.
- On `list`, a `when` over `document` filters rows: the caller receives only the
  records the rules admit.
- A caller without valid credentials gets 401. An authenticated caller no rule
  admits gets 403 with the first `reason` among the rules as `detail`, or
  `Forbidden`. A missing record answers 404 before any rule is checked.

## 10. Soft Delete

With `softDelete: true`, `DELETE` stamps a `deletedAt` timestamp on the record
instead of erasing it. A removed record is absent from `list` and answers 404
on `get`, `update`, `replace` and `delete`.

`deletedAt` is added to the collection as a read-only `datetime`; a request body
that sends it is rejected. A collection may declare `deletedAt` itself only as a
`datetime` field (`LIFECYCLE_FIELD_NOT_DATETIME`).

## 11. Pagination

`list` reads `limit` and `offset` query parameters:

- `limit` defaults to `api.pagination.defaultPageSize` and is clamped to
  `api.pagination.maxPageSize`. A `limit` that is zero, negative, blank or not a
  number answers 422.
- `maxPageSize` defaults to 100 and `defaultPageSize` to the smaller of 20 and
  `maxPageSize`. A `defaultPageSize` larger than `maxPageSize` fails the build
  with `PAGINATION_INVALID_SIZE`.

## 12. MongoDB Connection

```yaml
mongo:
  uri: ${MONGO_URI:-mongodb://localhost:27017}
  database: ${MONGO_DB:-blog}
```

`uri` defaults to `mongodb://localhost:27017` and `database` to `yaml_api`. See
[`mongo:`](../v0.2/Reference/configuration/mongo.md) for the variables the
development server and the generated apps read at run time.

## 13. Security

### CORS

Without `security.cors` no CORS headers are sent. With it:

| Key | Default | Meaning |
|---|---|---|
| `allowedOrigins` | `[]` | Origins allowed to call the API. |
| `allowCredentials` | `false` | Allow cookies and credentials. `"*"` in `allowedOrigins` is then rejected by the schema. |
| `allowedMethods` | `["*"]` | Methods allowed in preflight requests. |

Preflight requests receive the headers they ask for in
`Access-Control-Request-Headers`.

### Standard headers

`security.headers.enableStandard` (default `true`) adds these headers to every
response that does not set them itself:

| Header | Value |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `no-referrer` |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `Cross-Origin-Opener-Policy` | `same-origin` |

Set it to `false` when a proxy in front of the API adds them.

## 14. Build Errors

A spec that fails validation is not served or generated. Each error names its
code, the path of the offending key and, where one applies, a hint:

```text
spec.yaml:6:collections.posts.fields.views: error: default 'many' is invalid: Field 'collections.posts.fields.views' must be a number [FIELD_CONSTRAINT_INVALID]
    6 |       views: { type: number, default: many }
             ^
note: Make the default satisfy the field's own constraints or remove it
```

| Code | Cause |
|---|---|
| `SCHEMA_VALIDATION_ERROR` | An unknown key, a missing required key, or a value of the wrong type or outside its enum. |
| `UNSUPPORTED_VERSION` | `version` is not a supported spec version. |
| `INTERPOLATION_MISSING_VAR` | `${VAR}` with `VAR` unset. |
| `INTERPOLATION_MALFORMED_TOKEN` | A `${...}` that is not `${VAR}` or `${VAR:-default}`. |
| `INVALID_NAME`, `INVALID_FIELD_NAME` | A collection or field name that is not an identifier. |
| `NAME_PASCAL_CASE_COLLISION` | Two names that generate the same class name. |
| `ID_FIELD_MISSING`, `ID_FIELD_MULTIPLE` | A collection without exactly one `type: id` field. |
| `FIELD_CONSTRAINT_INVALID` | Inverted bounds, or a `default` that breaks its own field. |
| `REF_TARGET_NOT_FOUND` | A `ref` to an undeclared collection. |
| `AUTH_IDENTIFIER_FIELD_NOT_FOUND` | `auth.identifier` is not a field of the collection. |
| `AUTH_VIA_UNKNOWN_PROVIDER` | A `via` entry that is not `password`, `apiKey` or a `providers` key. |
| `AUTH_API_KEY_FIELD_MISSING` | `via: apiKey` without an `apiKey` field. |
| `AUTH_PASSWORD_FIELD_FORBIDDEN`, `AUTH_PASSWORD_HASH_FIELD_FORBIDDEN` | `password` or `passwordHash` declared with `via: password`. |
| `ROLES_DEFAULT_UNKNOWN_ROLE`, `ROLES_HIERARCHY_UNKNOWN_ROLE`, `ROLES_HIERARCHY_CYCLE` | Roles that are not declared, or a circular hierarchy. |
| `ACCESS_UNKNOWN_ENTITY`, `ACCESS_AMBIGUOUS_ROLE`, `ACCESS_NO_AUTH_ENTITY` | A principal that names no auth collection unambiguously. |
| `ACCESS_RULE_INVALID` | A `create` rule whose `when` names `document`. |
| `WHEN_EXPR_INVALID` | A `when` expression that does not parse. |
| `LIFECYCLE_FIELD_NOT_DATETIME` | A declared `deletedAt` that is not a `datetime` with `softDelete: true`. |
| `PAGINATION_INVALID_SIZE` | `defaultPageSize` larger than `maxPageSize`. |

## 15. Complete Example

```yaml
version: "0.1"

api:
  basePath: /api
  version: v1
  pagination:
    defaultPageSize: 20
    maxPageSize: 100
  operations:
    defaults:
      replace: false

mongo:
  uri: ${MONGO_URI:-mongodb://localhost:27017}
  database: ${MONGO_DB:-blog}

security:
  cors:
    allowedOrigins: ["${CORS_ORIGIN:-http://localhost:5173}"]
    allowCredentials: true
  headers:
    enableStandard: true

collections:
  users:
    type: auth
    auth:
      identifier: email
      via: password
    roles:
      values: [reader, editor, admin]
      default: reader
      hierarchy:
        admin: [editor]
        editor: [reader]
    operations:
      delete: false
    access:
      create: public
      list: "users:admin"
      get:
        - principal: "users:*"
          when: principal.sub equals document.id
          reason: Only the account owner can read it.
      update:
        - principal: "users:*"
          when: principal.sub equals document.id
    fields:
      id: { type: id }
      email: { type: string, required: true, unique: true, format: email }
      displayName: { type: string, required: true, minLength: 2, maxLength: 120 }
      metadata: { type: object }

  posts:
    softDelete: true
    access:
      list: public
      get: public
      create: "users:editor"
      update:
        - principal: "users:*"
          when: principal.sub equals document.authorId
      delete:
        - principal: "users:admin"
        - principal: "users:*"
          when: principal.sub equals document.authorId
    fields:
      id: { type: id }
      title: { type: string, required: true, minLength: 3, maxLength: 160 }
      body: { type: string, required: true }
      authorId: { type: ref, ref: users, required: true }
      tags: { type: array, items: { type: string } }
      published: { type: boolean, default: false }
      publishedAt: { type: datetime }
```

Anyone may sign up through `POST /api/v1/users` and becomes a `reader`. Readers
read and edit only their own account; an `editor` also writes posts and an
`admin` lists accounts and deletes any post. Authors edit and delete their own
posts, and a deleted post disappears from every route while its document keeps
a `deletedAt` stamp.
